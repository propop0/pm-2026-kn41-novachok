# Вибір підходу для трьох проєктів

Студент: Новачок Богдан, propop0. Тема проєкту: Телеграм-бот деканату.

## 1. Три кейси коротко

| Кейс | Обраний підхід | Критерій, який тягне проти | Ціна цього вибору |
| :-: | --- | --- | --- |
| C-1 | predictive | technology | Платимо гнучкістю реакції на раптові зміни в API реєстру |
| C-2 | adaptive | release_cost | Платимо потенційними репутаційними і фінансовими втратами при багах |
| C-3 | hybrid | contract | Платимо подвійним навантаженням на PM через підтримку двох форматів звітності |

## 2. Кейс C-1

Конфлікт критеріїв: Жорсткий контракт, фіксована дата подачі звітності та відсутній замовник однозначно вимагають предиктивного підходу. З іншого боку, сире і нестабільне API реєстру (технологія) є джерелом високої невизначеності і тягне в бік адаптивності. Оскільки контракт і вимоги регулятора неможливо змінити, переміг предиктивний підхід.

Що робимо з критерієм, який тягне проти: Закладаємо максимально можливий резерв часу на етапі розробки інтеграції (технологічний спайк) та інтеграційного тестування, щоб нівелювати непередбачуваність API.

Відкинутий підхід: Адаптивний. Плюс — дозволив би швидко підлаштовуватися під зміни API, мінус — неможливий через жорсткий Fixed Price контракт і відсутність замовника на регулярних демо.

Перший тиждень: Провести технічний спайк для стабілізації роботи з API реєстру та закласти буфер часу на очікування відповідей від їхньої підтримки, щоб одразу виявити всі блокери.

## 3. Кейс C-2

Конфлікт критеріїв: Відсутність фіксованого обсягу робіт, постійна зміна гіпотез після інтерв'ю та ідеальна для Agile команда диктують адаптивний підхід. Однак висока ціна помилки у платіжній частині (фінансові ризики, санкції банку) вимагає суворої предиктивної надійності. Переміг адаптивний підхід, бо стартап помре швидше від втрати ринку, ніж від локального бага.

Що робимо з критерієм, який тягне проти: Ізолюємо платіжне ядро від загальних швидких релізів, впроваджуючи для нього жорстке автоматизоване і ручне тестування перед викаткою.

Відкинутий підхід: Предиктивний. Плюс — дав би гарантовану надійність фінансового модуля, мінус — повністю б зупинив перевірку гіпотез, що є критичним для виживання стартапу.

Перший тиждень: Налаштувати автоматичні алерти на всі фінансові транзакції та запровадити обов'язкове перехресне рев'ю коду для платіжної частини, щоб мінімізувати ціну помилки релізу.

## 4. Кейс C-3

Конфлікт критеріїв: Старі дані без документації та постійні нові винятки в процесі (технологія і вимоги) вимагають ітеративного дослідження і тягнуть в адаптивний підхід. Але жорсткий річний бюджет (Fixed Price) і формальні протоколи зміни обсягу тягнуть у предиктивний. Переміг гібрид: ми фіксуємо бюджет і рамки, але досліджуємо вимоги ітераціями.

Що робимо з критерієм, який тягне проти: Розбиваємо фіксований річний бюджет на менші пакети робіт (мілстоуни), щоб мати формальні контрольні точки для фінансового директора, але зберігаємо гнучкість всередині цих пакетів.

Відкинутий підхід: Предиктивний. Плюс — повністю б задовольнив фінансового директора, мінус — призвів би до провалу на стадії міграції даних через величезну кількість неврахованих винятків.

Перший тиждень: Розділити проєкт на жорсткі фінансові етапи для контракту, але всередині першого етапу запустити короткі ітерації для швидкого виявлення винятків у вимогах та тестування міграції даних.

## 5. Стрес-тест контрактом

| Кейс | Рішення до конверта | Рішення після | Що змінилось у роботі PM |
| :-: | --- | --- | --- |
| C-1 | predictive, technology | adaptive | Події стали регулярними ітераціями; артефактом став беклог замість WBS; приймання змістилося з фінального акту на ітеративні демо; ризик перевитрати бюджету через нестабільне API переїхав із підрядника на замовника. |

Окремо: Два робочі ходи PM, коли контракт fixed price, а вимоги мінливі.
1. "Обмін обсягом" (Trading scope): замовник може додати нову вимогу, але за умови вилучення з беклогу іншої вимоги аналогічної трудомісткості, ціна ходу — складні переговори та аналітика оцінок.
2. Закладання буфера на зміни (Change Request Budget): виділення 15-20% бюджету/часу проєкту на старті спеціально під неминучі зміни, ціна ходу — ризик програти тендер через вищу початкову вартість.

## 6. Власний проєкт

Тема: Телеграм-бот деканату.

Обраний підхід: Адаптивний.

Чому саме так: З огляду на мій варіант (PM 50%, BA 100%, Dev 200%, QA 50%), команда дуже крос-функціональна і розробницька, а малий строк до релізу (20 тижнів) вимагає швидкої видачі цінності. Замовник (деканат) зазвичай перевантажений операційкою і вимоги до ботів формулює "на ходу" після перших демо. На ЛР1 ми вивели ризик "Команда вважає інтеграцію з базою абсолютно надійною". Адаптивний підхід ловить цей ризик тим, що ми покажемо реальну інтеграцію вже на першому демо (ЛР3), не чекаючи кінця розробки. На відміну від навчального C-1, у нас немає жорстких законодавчих регуляцій формату, а на відміну від C-2 — у нас не стартап, а внутрішній продукт університету.
