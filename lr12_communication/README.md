## 5. План комунікацій

| Поле | Значення |

| Рядків у `communication.csv` | 6 |

| Регулярних рядків / рядків `on_event` | 5 / 1 |

Ритм проєкту одним абзацом: оскільки строк нашого варіанта V06 становить **20 тижнів** (100 робочих днів базового строку і 110 днів з урахуванням критичного шляху), а довжина спринта дорівнює **2 тижням**, основним зовнішнім ритмом обрано двотижневий цикл (`biweekly` — 10 демо за проєкт) для показу приросту продукту замовнику `ST-01` (`C-01`) та інспекторам деканату `ST-04` (`C-06`). Для внутрішнього контролю дошки та черги в колонці `Review` (`WIP=2` при половинній ставці `QA 50%`) встановлено щотижневий (`weekly` — 20 разів за проєкт) звіт розробників для PM (`C-05`), а для зовнішніх контролерів зі стратегією `keep_satisfied` (`ST-02` юрист та `ST-03` адміністратор ІТ-служби) обрано щомісячний (`monthly` — 5 письмових звітів за 20 тижнів, `C-03` і `C-04`) ритм, щоб вчасно пройти віхи `T-16` та `T-17` без перевантаження їх щотижневими нарадами.

Рядок поганої новини: це рядок `C-02` (`channel = call`, `frequency = on_event`, `format = verbal`), адресований заступнику декана (`ST-01`). Його вмикає конкретна подія з нашого плану та реєстру ризиків: спрацювання тригера червоної зони `R-03` (за 3 робочі дні до контрольної віхи `T-16` у роботі `T-04` немає тестового токена API від адміністратора `ST-03`) або тригера `R-06` (зауваження юриста `ST-02` чи служби ІБ щодо блокування акта введення в експлуатацію перед віхою `T-17`).

Чого я свідомо не комунікую: я свідомо не виношу на замовника (`ST-01`) та юриста (`ST-02`) внутрішні технічні суперечки розробників, проміжні результати прогонів лінтера, деталі погашення технічного боргу (`D-01`–`D-04`) та поісторійні оцінки Planning Poker, а також не проводжу регулярних зустрічей зі старостами груп (`ST-06`, стратегія `monitor`), яких достатньо поінформувати один раз при запуску бота в роботу `T-14`.
